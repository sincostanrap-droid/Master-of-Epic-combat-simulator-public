# 公開版の更新手順

[ブラウザ版](https://sincostanrap-droid.github.io/Master-of-Epic-combat-simulator-public/) · [READMEへ戻る](../README.md)

このリポジトリは公開済みのツールを管理します。GitHub PagesはGitHub Actions方式で設定済みです。pushだけではサイトを更新せず、確認後に手動で公開します。

## 掲載・配信するファイル

- `release/github-files.txt`：リポジトリへ掲載するファイルの一覧。
- `release/web-files.txt`：Pagesで配信するファイルの一覧。
- `release/web-hashes.json`：配信ファイルのSHA-256。
- `.gitattributes`：配信ファイルの改行自動変換を止め、確認した内容をCIでも維持する設定。

必要な生成データ、技別JSON、ブラウザWorkerと動的読込先は配信対象です。未選別のファイルを一括追加せず、追加するファイルの内容と依存先を確認してください。生成データ内のメタデータも公開可能か確認します。

## 1. 更新前の確認

1. 作業開始時のcommitと、直前に正常公開したcommitを記録します。
2. ブランチ・送信先・未コミット変更を確認します。既存の変更をresetやcleanで消さないでください。リモートに更新がある場合は差分を確認して取り込みます。
3. 利用者の構成はJSONでバックアップします。ブラウザ保存領域は削除・初期化しません。保存形式を変更する場合は旧形式の読込と、戻す場合の互換性を検証します。

同じホスト内では、URLのパスが違ってもブラウザの保存領域は共有されます。登録や保存のテストは別ブラウザプロファイル等で隔離し、利用者の構成に試験用データを混ぜないでください。

## 2. 変更を反映して限定検証

1. 更新に必要なファイルだけを変更・反映し、差分を確認します。READMEや公開設定を古い内容で上書きしないでください。
2. 新しいファイルを追加した場合は、掲載一覧と配信一覧を必要に応じて更新します。Workerの読込先や遅延読込データの追加も確認します。
3. 配信対象の内容を確認してから、変更したファイルのSHA-256を更新します。ハッシュ不一致を消す目的で全件を自動更新しないでください。新規配信ファイルは`.gitattributes`にも追加します。
4. 変更に関係する入力変更・境界値・回帰を小分け・直列で検証します。通常の更新では全件テストや重い最適化を行いません。

Python 3.11以上で、毎回新しい出力名を指定して組み立てます。

```text
python tools/build-pages.py --output .local-preview/update-check-001
python -m http.server 8000 --bind 127.0.0.1 --directory .local-preview/update-check-001
```

上記は任意の検証用出力名です。出力先が存在すると停止し、既存のファイルは削除・上書きしません。ブラウザで出力フォルダの画面を確認したら、確認用サーバーを終了します。

## 3. 掲載差分を確定する

掲載対象の変更だけをファイル名を指定してステージします。`git add .`による一括追加は行いません。新規ファイルもステージした後、別の出力名で追跡ファイルの検査を実行します。

```text
python tools/build-pages.py --output .local-preview/update-strict-001 --check-git
```

掲載一覧外の追跡ファイル、不要な削除、個人の構成、秘密情報、改行だけの大量差分がないことを確認します。現在の件数を固定の正解とせず、確認した一覧・ハッシュ・依存関係との一致を検証します。

## 4. commit・push後に組立確認

確認した変更をcommitし、このリポジトリへpushします。

1. Actions → **Reviewed GitHub Pages** → **Run workflow** を開きます。
2. 既定ブランチ`main`を選び、`publish=false`で実行します。
3. buildの成功と対象commitを確認します。失敗した場合は原因を調べ、無条件で再実行しません。

ワークフローは許可一覧だけを新規の`_site`へコピーし、一覧とハッシュを照合します。掲載一覧外の追跡ファイルが残る場合も停止します。アップロードするのは`_site`だけで、リポジトリ全体ではありません。

## 5. 手動公開と公開後の確認

1. 組立確認に成功したcommitが`main`の先端であることを確認します。途中で更新された場合は新しいcommitの組立確認から行います。
2. 同じワークフローを`publish=true`で実行します。公開ジョブは既定ブランチのみ実行可能です。
3. buildとdeployの成功、公開したcommit、公開URLを記録します。
4. 公開URLで起動・変更した画面・代表計算を確認します。関係する場合は小規模な最適化や保存・復元も、利用者データから隔離して確認します。
5. ブラウザのエラー・データ読込漏れを確認します。ローカル確認と公開後確認は区別し、未確認の機能を確認済みとしません。

ブラウザ内の最適化Workerと、外部DB用Cloudflare Workerは別物です。`worker/`は保守用ソースでPagesには配信しません。外部サービスの変更が関係する場合は別に検証します。

## 不具合が出た場合

直前の正常公開commitを確認し、対象の変更をrevertして限定検証したうえで、push・組立確認・手動公開を行います。履歴のresetやforce pushで戻しません。

ブラウザ保存データはコードのrevertでは戻りません。利用者のデータを勝手に初期化せず、保存形式の互換性とバックアップを確認してください。

## 更新記録

開始commitと更新commit、変更内容、一覧・依存先の変更、限定テスト結果、Actions実行URL、公開commit、代表入力と計算結果、保存形式への影響、未確認範囲、戻せる正常commitを記録します。

設定の根拠：[GitHub公式：Pagesのカスタムワークフロー](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
